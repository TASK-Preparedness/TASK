# 6. Native PySide6 interface architecture

Proposal only; no UI or backend exists in this deliverable. **UNVERIFIED — REQUIRES PHYSICAL HARDWARE TEST**. Target uses the existing T.A.S.K. PySide6 launcher architecture [U69,U70]; Debian arm64 PySide6 Widgets is documented [S27]. Actual launcher embedding/window APIs remain source-review gates, not assumed `create_widget` or tile schemas.

## Integration boundary

- Dedicated tile “Firmware Manager”; proposed tile ID `task.firmware`, subject to Joshua's approval (not the Radio tile).
- One shared QWidget-based module view/controller, embeddable in launcher when its reviewed interface permits. A separate QMainWindow host uses the same view model and transaction authority, not a second independent flasher.
- Both views can observe a transaction; exactly one maintenance writer per physical device. “Open in separate window” transfers/attaches monitoring without restarting a subprocess, duplicating a lease or bypassing confirmation. Closing the integrated view cannot silently cancel or detach a risky operation.
- Local service adapter layers: vault/registry; image inspector/plan builder; task-core/task-comms ownership adapter; family backup adapter; esptool worker; transaction journal; progress/status model. These are proposed responsibilities, not existing class names or implemented APIs.
- QProcess or an equivalent bounded subprocess worker receives program and argument array, never a command string evaluated by a shell. Explicit `/usr/bin/python3`, stripped environment/PYTHONPATH, fixed tool path/version, no root GUI, no `shell=True`.

## Screens

1. **Devices:** passive USB candidates, persistent identity/USB topology, owner/status, denylisted GPS visibly protected, board revision confirmation, RF chip/band, confidence evidence. Unknown board/owner cannot proceed; VID/PID alone shows only a candidate.
2. **Local library:** family/version/board/role filters, stored and available-offline status, original source/license and trust, SHA256, test level, matching/mismatching reason. Unknown/unqualified artifacts remain disabled.
3. **Inspect/import:** user-selected USB/local files; quarantine, image metadata, matched registry, full component set, compatibility conflicts and disk requirement. Optional online acquisition separated and default off.
4. **Prepare:** chosen device + owner, board/role warning, recovery guide, stable power requirement, backup support and limitations, maintenance outage approval. No reset/probe on opening this screen.
5. **Plan/confirm:** exact old/new family/version/role, write/erase regions, identity/MAC, verified hashes, potential key/bond/history loss, actual backup result and RF startup policy. Explicit typed confirmation; erase checkbox cannot be hidden under a normal update button. No remembered confirmation or “always allow.”
6. **Progress:** release, probe/bootloader, backup, erase, individual segments, byte verification, boot quarantine, approved reconnection, ownership return. Display real bytes/stage output; indeterminate progress for unknown stages, never fabricated countdowns or “100% success” at tool exit.
7. **Result/recovery:** separate “bytes written,” “verified,” “firmware identified,” “owner reacquired” and “not tested” results. Persist a local redacted report. Failed recovery offers offline board-specific steps, not an automatic erase/reflash.
8. **History/settings:** transaction evidence, retained images, private backup coverage, license notices, explicitly selected export with redaction preview. No automatic uploads, network checks, telemetry, media autorun or scheduled flashing.

## Privacy, accessibility and operational rules

Follow existing task-comms notification privacy/filter controls after review. Desktop notification body contains generic stage/failure only, not keys, private node names, positions or MACs. No new audio asset is needed; no global Qt, Bluetooth or audio setting changes. Preserve working Mesh notifier exactly.

Use keyboard/touch-friendly layout, clear offline status, high-contrast destructive warnings, accessible text labels rather than color alone, scrollable plan details and a persistent “GPS protected” indication. UI must remain responsive during long jobs. Before write, Cancel simply exits maintenance after safe reacquire; after erase/write, the warning explains interruption risk and does not promise cancellation can restore the device. A crash-safe worker/journal contract needs review before production use.

Core functionality is native and local. Offline HTML/Markdown recovery documentation may be rendered as simple local text; no external website, sandbox-disabling browser, root webview or internet dependency is required.
